# Online Boutique with HTML-form request bodies (2026-10-15, round 11c)

## Purpose

In `../verdict_table_20261015b/` the positive tests of Online Boutique's `POST /cart`,
`POST /cart/checkout` and `POST /setCurrency` went out with no body and got 422. The cause was in
MIST. Stage (i) read only `application/json` request bodies, so an operation whose body is sent as
`application/x-www-form-urlencoded` (a Swagger 2.0 `formData` operation after conversion) lost its
fields, and the writer had no way to send a form. Commit 06f4737c fixes both: stage (i) reads a
form-only body's fields like a JSON body's and records `requestContentType` on the operation, the
generator form-encodes the body, and the writer sends it with the form media type. Bookinfo, Sock
Shop and TrainTicket have no form-only request body, so the fix leaves their configurations and
their rows unchanged.

Sending real form bodies exposed a second gap, fixed in commit f4e52caf. With the language model
off, MIST invented string values as `test<n>`, which it did not recognize as invented, so a positive
test that sent one still expected 2xx. It now invents `FALLBACK_test<n>`, and such a test is marked
negative in advance like any other test with an invented value. The same commit leaves a null field
out of a form, so a null-input and an empty-input negative test send different requests.

This folder holds the two Online Boutique legs re-run with the fixed jar. They replace the Online
Boutique rows of `../verdict_table_20261015b/`; the Bookinfo rows there and the Sock Shop and
TrainTicket rows of `../verdict_table_20261014/` stay.

## Method

- Jar: built from the code of commit f4e52caf with `mvn -Dmaven.test.skip=true install`
  (2026-10-15 12:35); `mist-core`'s 402 unit tests pass.
- Configuration: `evaluation/suts/boutique/real-system-conf.yaml`, regenerated by the fixed stage (i)
  (`io.mist.cli.MistConfGenMain`). It differs from the earlier file only in the three form
  operations, which now carry their fields (`product_id`, `quantity`; the ten checkout fields;
  `currency_code`) and `requestContentType: application/x-www-form-urlencoded`. The earlier file is
  `git show 3aa6c9ec:evaluation/suts/boutique/real-system-conf.yaml`.
- Profile: `evaluation/suts/boutique/boutique-hdf-r11c.properties`, the round-11b profile (request
  dedup, one captured entry call per scenario, status-code exploration and the test enhancer off,
  traces from `traces-r11b/`) with the bundle's demo generation settings (`faulty.ratio=0.8`,
  `test.variants.per.scenario=10`, `testsperoperation=20`, as in the profile of the Sock Shop row)
  in place of the round-11 values. With the round-11 values the form operations
  gave about 470 more positive tests per leg, nearly all the same operation with other invented
  values. Request dedup kept 543 of the 871 tests the generator produced in each leg (the
  `Request dedup` line of MIST's runtime log).
- Trace wait before each lookup: five seconds in both legs; every test lasted at least 5.0 s
  (Allure start and stop times).
- Outage: `adservice` scaled to 0. Probes before each leg (`driver.log`): `/` and
  `/product/OLJCESPC7Z` 200 in both legs. The rest of the namespace ran without the load generator.
- Sequence: `run_boutique_r11c.ps1` ran both legs through `../verdict_table_20261015/run_leg.ps1`
  and scaled the namespace back to 0; it is the script as run, with the scratch output directory
  replaced by a `-Root` parameter, and `boutique-c-seq.log` is its log (that directory written as
  `<run dir>`). `stage_leg.py` copied each leg here.
- Tables and checks: `analyze_leg.py` and `negatives.py` of `../verdict_table_20261015/` and
  `source_distinct.py` of `../verdict_table_20261015b/`, with the definitions of
  `../verdict_table_20261014/README.md`.

target the fields of the three form operations.

## Distinct requests

`source_distinct.py` over `generated-tests.zip`, restricted to the tests of `verdicts.csv`: 543 tests

## The response classifier with the model off

The classifier made no judgment of its own: every 2xx positive response got an empty model
response, which MIST records as "VALID SUCCESS" with the explanation "LLM validation failed: ...
llmResponse is null". No response was flagged: no "SOFT ERROR DETECTED" in either leg, and every
RESPONSE_ENVELOPE check passed.

## Per-leg files

Each leg folder holds `allure-results.zip`, `generated-tests.zip`, `driver.log`, `mist-<leg>.log`,
the fault-detection summary, `verdicts.csv` and `scan.csv`, as in `../verdict_table_20261015b/`.
In each leg about 465 tests carry no trace verdict (468 without and 465 under the outage): the
frontend answered them with 422 or 404 (median 6 ms, at most 187 ms), and the trace lookup found no
span ("Jaeger Query Debug (No Traces)"). None of them is 2xx.
